Kinglet ships with real user accounts: email + password sign-in, server-side
sessions in an HttpOnly cookie, three built-in roles, and multiple projects
with their own API keys.

Authentication is powered by [Better Auth](https://better-auth.com) with the
Drizzle adapter, tuned per its performance guide:

- `better-auth/minimal` — Kysely is not bundled (Drizzle handles the database).
- **Session cookie cache** (`60s`) — `getSession` reads a signed cookie
  instead of hitting the database on every request.
- **Indexes** on `user.email`, `session.userId`/`token`, `account.userId`, and
  `verification.identifier`.
- Public self-signup is disabled; accounts are created by administrators.

## First boot

When no administrator exists — first boot, or recovery from a database with no
admin account — Kinglet creates or promotes one:

| Env var | Default | Notes |
| --- | --- | --- |
| `KINGLET_ADMIN_EMAIL` | `admin@kinglet.local` | login identifier |
| `KINGLET_ADMIN_PASSWORD` | *(generated)* | printed once; written to `admin-password.txt` only for local databases |

These only apply when no administrator exists — changing them while an admin is
present does nothing. If an account with the configured email already exists, it
is promoted and keeps its current password. The administrator cannot be deleted.

## Passwords

New and changed passwords set through the UI or the admin user API must be at
least **12 characters** and include a lowercase letter, an uppercase letter, and
a number. The UI shows a live checklist and a show/hide toggle on every password
field. Existing shorter passwords still sign in; the policy applies when a
password is set or changed.

Administrators can leave the password blank when creating a user — Kinglet
generates a 16-character password that meets the same policy and shows it once.

## User actions

Admins can reset a user's password, change their role, disable or enable the
account, or delete it from the user actions menu.

- **Change role** switches a user between member and viewer.
- **Reset password** generates a compliant password, shows it once, and signs
  the user out everywhere.
- **Disable** blocks sign-in and invalidates keys minted by that user until the
  account is enabled again.
- **Delete** removes the account and its sessions; administrators cannot be
  deleted or disabled, and you cannot disable or delete your own account.

## Roles

| Role | Can do |
| --- | --- |
| **admin** | everything: projects, users, keys, logs, monitors. Cannot be deleted or demoted while last |
| **member** | read/write logs, manage monitors, manage API keys |
| **viewer** | read logs, monitors, and project metadata |

Roles map to explicit permission keys (`logs.read`, `monitors.write`,
`keys.write`, `users.read`, …) internally, so custom roles later are a data
change rather than a refactor.

<Aside type="note" title="Project access">
  Roles set what a user can do; project membership sets where they can do it.
  Admins see every project. Members and viewers see only the projects assigned
  to them in **/settings → projects & keys**.
</Aside>

## Project membership

Admins always have access to every project. Everyone else needs a
`project_members` assignment:

- **Members** get their role's write capabilities (logs, monitors, keys)
  inside assigned projects.
- **Viewers** get read-only access inside assigned projects.
- **Clear logs** is a separate per-project grant. Admins always have it;
  members can be granted it from the member list; viewers cannot. It is off by
  default.
- Assign or remove people in **/settings → projects & keys** while the project
  is selected.
- Upgrading from an older Kinglet backfills every user into every existing
  project, so nobody loses access; prune assignments afterwards.

The API exposes this as `GET`/`POST /v1/projects/:id/members`,
`PATCH /v1/projects/:id/members/:userId` (`{ "canClearLogs": true|false }`), and
`DELETE /v1/projects/:id/members/:userId` (admin only). A non-member requesting
another project's data gets a `404`, so project ids cannot be probed.

## Projects

Every project owns its events, monitors, alert history, and API keys. Switch
projects from the header dropdown; the logs, histogram, live tail, monitors,
and alerts all follow. Admins create and delete projects in **/settings**.

### Clearing logs

Admins, and members granted **clear logs**, can delete a project's events from
**/settings → projects & keys → Clear logs**. Pick a preset range (last hour,
6 hours, 24 hours, 7 days, 30 days), all time, or a custom start/end. Keys,
monitors, and alert history are left alone. The grant is per project, off by
default, and cannot be given to viewers.

## API keys

Machine credentials live per project with explicit **scopes** — a key never
inherits a human role:

| Scope | Allows |
| --- | --- |
| `ingest` | `POST /v1/events` |
| `query` | `GET /v1/events`, `/v1/histogram`, `/v1/services`, `/v1/stream` |

Keys look like `kl_…` and are shown **once** at creation. Revoke them any time
in **/settings → projects & keys**; the list keeps a display prefix, scopes,
creator, and last-used time. A key created without an explicit `scopes` array
defaults to `["ingest"]`; unknown scopes are rejected with a 400. When a user is
demoted or deleted, keys they created are revoked.

The key actions menu can also **edit permissions** (change `ingest`/`query`
scopes without replacing the key) and **reroll** it. Rerolling immediately
invalidates the old plaintext and shows the new one once. **View usage** filters
the logs to `key:<id>`, so you can see what each key has been sending.

```bash
curl -X POST http://localhost:8080/v1/events \
  -H "Authorization: Bearer kl_…" \
  -H "Content-Type: application/x-ndjson" \
  --data-binary '{"level":"info","message":"hello","service":"my-app"}'
```

API keys are bound to their project — no `?project=` needed, and they cannot
list projects, manage monitors, or touch users.

## How auth is resolved

1. `Authorization: Bearer kl_…` → project-scoped API key
2. `better-auth.session_token` cookie → signed-in user, with role permissions

Browser routes accept the cookie; project-scoped calls use `?project=<id>`.
SSE accepts `?key=` for shipper-style clients that cannot send headers. Sessions
last `KINGLET_SESSION_DAYS` (default 30). Role changes and account deletion
delete the user's sessions and API keys; mutating requests always bypass the
cookie cache, so a demoted user cannot keep writing.

<Aside type="caution" title="Run behind TLS">
  Session cookies are HttpOnly + SameSite=Lax and become `Secure` when
  `KINGLET_BASE_URL` is an HTTPS URL. For anything beyond localhost, set
  `KINGLET_BASE_URL` and put Kinglet behind Caddy/nginx TLS.
</Aside>
