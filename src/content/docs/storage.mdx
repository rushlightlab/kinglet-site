Kinglet uses **one engine for both modes**: the libSQL client, which opens a
local SQLite file by default or connects to a hosted [Turso](https://turso.tech)
database with the same code. Schema and queries are defined once with
[Drizzle ORM](https://orm.drizzle.team); migrations live in
`apps/api/drizzle` and are applied automatically on boot.

**sqlite (default)** — a single local database (plus WAL/SHM sidecars while running), zero config, zero services:

```bash
KINGLET_DB_PATH=/data/kinglet.db
```

WAL mode and the FTS5 trigram index are configured automatically.

### Search index

`KINGLET_SEARCH` picks how message text is indexed. The index is the largest
single cost of ingest, so this is the main knob for high-volume installs.
Measured over HTTP in a 2-vCPU Docker VM with ~500k ~200-byte events:

| Mode                    | Matches                                      | Ingest      | Disk / 1M events | Peak RAM |
| ----------------------- | -------------------------------------------- | ----------- | ---------------- | -------- |
| `substring` _(default)_ | any 3+ character fragment                    | ~7,300 ev/s | ~0.55 GB         | ~410 MB  |
| `words`                 | words and word prefixes (`time` → `timeout`) | ~8,900 ev/s | ~0.42 GB         | ~220 MB  |
| `off`                   | substrings, by scanning the selected window  | ~9,400 ev/s | ~0.38 GB         | ~190 MB  |

With `off`, a filter on a common term still returns quickly (the newest
matches are found first), but a rare term or a count scans every event in the
window: roughly 0.5 s with half a million events in range. Changing the mode rebuilds (or drops)
the index once at boot. The live tail always matches substrings.

**Turso** — point at your database; nothing else changes:

```bash
KINGLET_DB_PATH=libsql://your-db.turso.io
KINGLET_DB_AUTH_TOKEN=eyJ…
```

With `KINGLET_STORAGE=auto` (the default), a plain path uses the local file and
`libsql://`, `https://`, `wss://`, or `file:` URLs use the libSQL transport.

<Aside type="note" title="One engine, two transports">
  Earlier versions had separate better-sqlite3 and libSQL drivers. They are now one libSQL client —
  the same query code, schema, and migrations run locally and on Turso.
</Aside>

### Notes for hosted Turso

```bash
docker run -d --name kinglet -p 8080:3000 \
  -e KINGLET_DB_PATH=libsql://your-db.turso.io \
  -e KINGLET_DB_AUTH_TOKEN=eyJ… \
  -e KINGLET_ADMIN_EMAIL=you@example.com \
  -e KINGLET_ADMIN_PASSWORD=change-me-please \
  ghcr.io/rushlightlab/kinglet:latest
```

- **One Kinglet instance per database.** Ingest assumes a single writer.
- **Every query is a network round trip.** Keep ingest batched; each enabled
  monitor's count check costs one round trip per interval.
- **Backups are Turso's job.** Litestream applies to local SQLite files only.
- Schema and migrations run automatically on first boot, same as a local file.

## Migrations

Schema changes are generated by Drizzle Kit and applied on boot. For local
development:

```bash
pnpm --filter @kinglet/api db:generate   # create a migration after schema edits
```

The generated SQL is reviewed and committed; the app runs it before serving.

## ClickHouse (roadmap)

When a single node stops being enough, a ClickHouse engine implementing the
`Storage` interface is the graduation path for the event/query path — the API
and UI won't change.
