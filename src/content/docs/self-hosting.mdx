## Deploy

Kinglet ships as a multi-arch image (`linux/amd64` + `linux/arm64`) at
`ghcr.io/your-org/kinglet` — the repo's release workflow publishes it (see
[Publishing images](#publishing-images)).

```yaml
# docker-compose.yml
services:
  kinglet:
    image: ghcr.io/your-org/kinglet:latest   # pin a version in production, e.g. :0.1.0
    ports:
      - "8080:3000"
    environment:
      KINGLET_DB_PATH: /data/kinglet.db
      KINGLET_RETENTION_DAYS: 14
    volumes:
      - kinglet-data:/data
    restart: unless-stopped

volumes:
  kinglet-data:
```

```bash
docker compose up -d       # pulls the right architecture automatically
```

<Aside type="tip" title="Building from source">
  No published image? Clone the repo and swap `image:` for `build: .` —
  `docker compose up -d --build` produces the same image locally.
</Aside>

<Aside type="note" title="Pinning versions">
  Use release tags in production (`:0.1.0`) so upgrades stay deliberate —
  `:latest` moves on every push to `main`. Available tags are listed on the
  repository's packages page.
</Aside>

<Aside type="caution" title="Private packages">
  GHCR packages start private even when the repository is public. For
  anonymous `docker pull`, make the package public once (Packages → kinglet →
  Package settings → Change visibility → Public). Otherwise run
  `docker login ghcr.io` first.
</Aside>

### Publishing images

`.github/workflows/docker.yml` builds and pushes the image:

| Trigger | Tags |
| --- | --- |
| push to `main` | `:latest`, `:main`, `:sha-<commit>` |
| push tag `vX.Y.Z` | `:X.Y.Z`, `:X.Y`, `:latest` |

```bash
git tag v0.1.0 -m "Kinglet v0.1.0"
git push origin v0.1.0
```

## Configuration

| Env var | Default | What it does |
| --- | --- | --- |
| `KINGLET_PORT` | `3000` | HTTP port inside the container |
| `KINGLET_STORAGE` | `auto` | `sqlite`, `libsql`, or `auto` (picks by db path scheme) |
| `KINGLET_DB_PATH` | `data/kinglet.db` | Plain path → SQLite; `libsql://`/`https://`/`file:` → libSQL |
| `KINGLET_DB_AUTH_TOKEN` | — | Auth token for remote libSQL/Turso |
| `KINGLET_ADMIN_EMAIL` | `admin@kinglet.local` | Bootstrap administrator email (first boot only) |
| `KINGLET_ADMIN_PASSWORD` | *(generated)* | Bootstrap administrator password (first boot only) |
| `BETTER_AUTH_SECRET` | *(generated, persisted)* | Session signing secret — set explicitly for multi-instance installs |
| `KINGLET_TRUSTED_PROXIES` | — | CIDRs allowed to set `X-Forwarded-For` |
| `KINGLET_ALLOW_PRIVATE_WEBHOOKS` | — | Allow private/internal webhook targets (SSRF escape hatch) |
| `KINGLET_SESSION_DAYS` | `30` | Web session lifetime |
| `KINGLET_TOKENS` | *(auto-generate)* | Legacy global tokens — all projects, full access |
| `KINGLET_RETENTION_DAYS` | `14` | Delete events older than this |

## Sizing

- **RAM**: ~150–250 MB steady state.
- **CPU**: 2 vCPUs comfortably handle millions of events per day — ingest is
  batched SQLite writes, not per-request round trips.
- **Disk**: roughly 300–500 MB per million retained events. With the default
  14-day retention, a busy small app stays in single-digit gigabytes.

## Backups

The whole store is one file. [Litestream](https://litestream.io/) replicates
it continuously to S3-compatible storage with a one-line sidecar:

```yaml
litestream:
  image: litestream/litestream
  volumes:
    - kinglet-data:/data
  command: replicate /data/kinglet.db s3://your-bucket/kinglet
```

## TLS and upgrades

- Put Caddy or nginx in front for automatic TLS, or use a `caddy` compose
  profile; the container speaks plain HTTP on its port.
- Upgrades: `docker compose pull && docker compose up -d`. Graceful shutdown
  flushes SQLite on `SIGTERM`, so `docker compose stop` is safe.

<Aside type="tip" title="ARM64">
  Low-end VPS deals are often aarch64 — build the image for both platforms
  with `docker buildx build --platform linux/amd64,linux/arm64`.
</Aside>
