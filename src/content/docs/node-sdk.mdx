`@kinglet/sdk-node` is a zero-dependency batching client for Node 24+. Events
buffer in-process and ship as a single NDJSON batch — 1,000 events or every
second, whichever comes first. A failed batch is re-queued (with a cap) and
reported through `onError`, so your app never blocks on logging.

## Install

<PackageManagers pkg="@kinglet/sdk-node" />

## Projects and keys

There is no `project` option. A Kinglet API key is bound to one project on the
server, so the key you pass as `token` selects where the events go. Create a
key with the **ingest** scope in **Settings → Projects → manage**, and use a
separate key for each project or environment.

`service` and `env` only tag events for filtering — they don't route them.

## Use

```ts
import { createLogger } from "@kinglet/sdk-node";

const log = createLogger({
  url: "http://localhost:8080", // your Kinglet server
  token: process.env.KINGLET_KEY!, // project key with the ingest scope (kl_…)
  service: "my-app",
  env: "prod",
});

log.info("user signed in", { userId: 42 });
log.error("payment failed", { orderId: 1234, code: "card_declined" });

// best-effort final flush in your shutdown handler
await log.close();
```

## TypeScript

The SDK is written in TypeScript and builds with declaration output, so
`dist/index.d.ts` ships alongside the JavaScript. `Logger`, `LoggerOptions`,
and `LogFields` are exported — no separate `@types` package is needed:

```ts
import { createLogger, type Logger, type LoggerOptions, type LogFields } from "@kinglet/sdk-node";
```

It is ESM-only (`"type": "module"`, with an `import` export) and requires
Node 24 or newer.

## Options

| Option            | Default | What it does                                                           |
| ----------------- | ------- | ---------------------------------------------------------------------- |
| `url`             | —       | Kinglet base URL (required)                                            |
| `token`           | —       | `kl_…` key with the ingest scope (required) — also selects the project |
| `service` / `env` | —       | tagged onto every event                                                |
| `batchSize`       | `1000`  | flush after this many buffered events (max 5000)                       |
| `flushMs`         | `1000`  | flush at least this often                                              |
| `onError`         | —       | called when a flush fails; the batch is re-queued                      |

Every non-2xx response is re-queued, including `401`, `403`, `413`, and `422`,
which will not succeed on retry. Use `onError` to spot a revoked key or an
oversized batch.

## Methods

| Method            | What it does                                    |
| ----------------- | ----------------------------------------------- |
| `trace` … `fatal` | buffer one event with an optional fields object |
| `flush()`         | send the current buffer now                     |
| `close()`         | wait for a request in flight, then drain buffer |

## Why 1000 events per batch

Most apps never fill a batch: below a few hundred events a second, the
one-second timer flushes first and the batch size changes nothing. It matters
for busy services:

- **Rate limit.** Ingest allows 600 requests per minute per key. At 200 events
  per request that caps one key near 2,000 events/s; at 1,000 it is 10,000,
  more than one server sustains (see [Capacity planning](/capacity/)).
- **Server cost.** Each request pays fixed work (auth, parsing, a commit).
  1,000-event batches ingest roughly 25% faster per event than 100-event ones.
- **Outage buffer.** The client keeps up to 10 batches in memory while the
  server is unreachable, so a larger batch also rides out a longer restart.

The trade-off is memory (up to 10,000 buffered events) and, on a hard crash,
losing up to one batch or one second of logs, whichever is smaller. Lower
`batchSize` if your events are large; one request never carries more than 5,000
events.
